# Shared style rules live in TypeScript, not in the theme

Status: accepted

Three class strings repeated across components with no design reason to differ, so a change to any one of them meant editing between three and five files and a missed file drifted silently (issue #46). The issue left the mechanism open: a Tailwind `@utility` in the theme CSS (Option A), or shared TypeScript constants in `src/registry/lib/` (Option B). This ADR takes Option B and fixes the rules that decide what may move there.

## Decision

- **Shared style rules ship as TypeScript constants, not as theme utilities.** A consumer's `cn()` comes from the shadcn CLI's own template — stock `twMerge(clsx(...))`, not built with `extendTailwindMerge`. A custom `@utility` is therefore invisible to tailwind-merge in every install, so a consumer's `className` override of it silently loses. `alert.tsx:112` is the live proof: its dismiss button overrides the shared ring offset with `focus-visible:ring-offset-card`, and that override works today only because the shared value is a plain Tailwind class. Option A was available — shadcn 4.19.0 does support `@utility` in a registry item's `css` key — and is rejected on merit, not on tooling limits. This follows `src/registry/lib/motion.ts`, where ADR 0001 already put design values in TypeScript beside the CSS custom properties.
- **The bar for centralising: a class string moves to a shared module when an ADR or `CONTEXT.md` rule stands behind it. Byte-identity alone is not the bar.** The disabled state has ADR 0004. The two focus rings have ADR 0003. The field label has the field family in `CONTEXT.md`. Everything that merely rhymes stays duplicated — the `read-only:*` pair in input and textarea is byte-identical across two adjacent files and stays inline, because no rule stands behind it and `read-only:focus-visible:border-muted` is a color choice.
- **Two modules, split by who shares the rule.** `src/registry/lib/interaction.ts` holds what every interactive component shares regardless of family: `disabledInteraction`, `offsetFocusRingGeometry`, `boundaryFocusRingGeometry`, `invalidBoundaryFocusRingGeometry`. `src/registry/lib/field.tsx` holds `fieldLabelVariants`, for the field family only. Routing button and switch through `field` would force a semantically false dependency and drag `motion/react` and `FieldErrorMessage` into every button install for two class strings.
- **`interaction.ts` stays dependency-free.** No `cn`, no `cva`, no `clsx`. It installs as a leaf, and that leafness is what makes the extra `registryDependencies` entry cheap for five items.
- **The ring exports carry geometry; the component names its own ring color.** Ring color is variant-dependent in two of the three offset consumers — button supplies `ring-primary` / `ring-ring` / `ring-destructive` across five variants, checkbox supplies it from its `error` variant. A constant its callers must override is worse than no constant. Switch keeps its single `focus-visible:ring-ring` in its own base, beside the shared geometry rather than inside it. **A component that takes a ring export and names no ring color renders ring width with no visible ring, silently.** The module cannot enforce this; the `interface-review` checklist carries it.
- **Two names, never one — and taking neither is a valid third answer.** ADR 0003 owns the geometry and fixes two widths by where the ring draws. Do not restate the widths here. Pick with ADR 0003's question: a ring that stands off the shape takes `offsetFocusRingGeometry`; a ring that draws on the element's own boundary and replaces its border takes `boundaryFocusRingGeometry`. A single combined focus-ring name would collapse the two widths and break ADR 0003. ADR 0003 also allows a component to show focus without a ring when its own state indicator moves with focus (tabs). That component imports neither export, and its absence from this module is a decision rather than an oversight — the same status card already has.
- **`ring-offset-background` and `focus-visible:border-background` are geometry, not color.** The offset surface is the default surface the ring stands off, not a variant choice, and it stays overridable through tailwind-merge (`alert.tsx:112`). The boundary form's border-blanking is geometry because ADR 0003's own wording is "replaces its border" — you cannot state the rule without blanking the border.
- **The invalid state's border-blanking is shared; its colors are not.** `aria-invalid:focus-visible:border-background` is functionally required, not decorative: `focus-visible:border-background` and `aria-invalid:border-destructive` are both specificity (0,2,0), so the destructive border wins on source order and the two-variant form is what restores the blanking. It ships as `invalidBoundaryFocusRingGeometry`. Its two destructive colors — `aria-invalid:border-destructive` and `aria-invalid:focus-visible:ring-destructive` — stay in input and textarea.
- **Card is excluded from the ring exports, and restates the boundary width itself.** Card paints its ring on a `::after` of a descendant link (`[&>a]:focus-visible:after:ring-2`), so the flat geometry string cannot apply as written. The exception is about how many pseudo-element rings exist, not about card. If a second stretched-link component appears, the answer is a selector-prefixed form of the same export, not a second hand-written copy.
- **Switch's label is excluded from `fieldLabelVariants`.** A label joins the shared variants when its component is a field family member. Switch is not one, has no error state, and transitions opacity rather than color. It keeps its own block by rule.
- **`fieldLabelVariants` takes a required `placement`, with no default.** The variant is named after the layout fact — `above` for input and textarea, `beside` for checkbox — not after the pixel, because a future field author knows where their label goes and does not know whether they want 8px. It takes no default: defaulting to `above` and letting checkbox omit the prop would silently add `mb-2` inside checkbox's `flex items-center` row and shift the label off the box's vertical center, with no test to catch it. Required turns that into a type error at all three call sites.
- **Every `registryDependencies` entry carries the `@flyingsalmon/` prefix.** A bare name resolves against shadcn's own registry, and every item name in this registry collides upstream, so a bare entry installs another vendor's component and fails silently rather than with a 404. Verified end to end: `shadcn build`, served locally, then `shadcn add` into a fresh consumer delivers shadcn's own `Field`, `Label`, `Separator` and `Spinner` for bare names, and this repo's files for namespaced ones. The existing bare entries are fixed here alongside the new ones.
- **These rules are enforced by prose, review and the `interface-review` checklist.** oxlint 1.79.0 cannot express a restricted-syntax rule for them, and a test asserting where a class literal may appear is a change detector, which this repo bans. The enforcement is a decision, not an oversight.

## Rationale

- Option B keeps tailwind-merge behaving exactly as it does today, in this repo and in every consumer. Option A's only advantage is authoring ergonomics, and it buys that by breaking `className` override in installs this repo cannot reach or patch.
- The stated cost of Option B — one `registryDependencies` entry per item — turned out to be the wiring that was already broken. Fixing the namespacing makes the cost real rather than theoretical.
- Naming the rings after the rule rather than the pixels means the next component author picks by asking ADR 0003's question instead of copying whichever neighbour they opened first.

## Consequences

- **This reverses part of PR #45 (issue #34), and the reversal is deliberate.** PR #45 kept the label block duplicated on purpose, because a shared `FieldLabel` component would have needed props for spacing and for the destructive-on-error rule to cover all three shapes. **That rejection still stands: no `FieldLabel` component ships.** What supersedes it is narrower — a variants function absorbs the placement difference as a variant and leaves the `<label>` element in each component file, where a consumer can edit it in place. The cva refactor in PR #47 changed the shape of the problem; #45's objection was to the component, and this is not one.
- **The button's outline handling changes, and it is consumer-facing.** `button.tsx` carried `outline-none` unprefixed; the shared export carries `focus-visible:outline-hidden`. `outline-none` sets `--tw-outline-style: none` unconditionally, so a consumer writing `outline-2` on a Button gets nothing today and will get an outline after this. No such call site exists in this repo, so no docs page surfaces it.
- **Every ring consumer moves from `outline-none` to `outline-hidden`.** `outline-hidden` keeps a transparent outline under `forced-colors: active`, which is strictly better for the WCAG AA requirement this repo calls hard. The browser-outline half is otherwise near-inert: the compiled stylesheet's only outline hook is preflight's `:-moz-focusring`, drawn at `:focus-visible`, which both forms suppress.
- `src/components/theme-toggle.tsx` shipped a third ring geometry ADR 0003 does not define — `ring-3` with no offset and no offset surface. It now takes `offsetFocusRingGeometry` and names its own `focus-visible:ring-ring`, so the docs chrome matches button and checkbox. It is the module's first non-registry caller.
- `field` gains `class-variance-authority` in its `dependencies`, because it now imports `cva`. Its three current consumers already declare it, so nothing regresses; a consumer installing `field` alone would have broken.
- **The press ring is the nearest future candidate and is deliberately not hoisted.** ADR 0003 covers it ("The press ring stays 2px in every case"), so it clears the bar above, but its only two consumers are the button and card pair the card exclusion already splits — hoisting it would leave a one-real-caller export and a hand-written copy in card. Hoist it when a third consumer arrives, or when card's pseudo-element form gets a selector-prefixed export.
- **Drift becomes structurally impossible between importers, and no more than that.** Three strings now have one definition each. The condition that produced the drift is untouched: this repo's design rules live only in ADR prose, and conformance rests on a contributor remembering that prose while authoring. This ADR adds four more prose-only rules. The condition has already fired once undetected, in `theme-toggle.tsx`. Recurrence at component twelve stays possible.
- A future sibling sweep must key on the tokens drift leaves behind — `ring-3`, `outline-none`, `disabled:opacity` — not on the tokens drift removes, and must cover `src/components/` and `src/routes/`, not only `src/registry/`. A search keyed on `ring-offset-2` finds only copies that have not drifted.

## Flip condition

If the shadcn CLI's template ever ships a `cn` built with `extendTailwindMerge`, or tailwind-merge gains config-driven discovery of custom utilities, Option A's cost disappears and the theme becomes the better home for these rules. Amend this ADR then and move the class strings into the theme's `css` key, keeping the two ring names.
